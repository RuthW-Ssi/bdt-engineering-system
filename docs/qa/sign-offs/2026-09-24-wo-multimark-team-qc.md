## findings

**F-001 (High → BLOCK)**
- **where:** `backend/prisma/migrations/20260922000000_mo_plan_actual_dates/migration.sql`
- **what:** `ALTER TABLE "manufacturing_order" DROP COLUMN "due_date"` with **no backfill** into any of the new `plan_start`/`plan_finish`/`actual_start`/`actual_finish` columns. Unlike every other destructive statement in this migration set, `due_date` is **not** a column born in this branch — it was added `2026-06-15` (`20260615120000_sprint13_manufacturing_order`), is actively read and written by `manufacturing-orders.service.ts` (list rows, create, update) on `origin/dev`, and is displayed to users on `MoDetail.tsx` ("Due Date" row). Every other migration in this set that drops a column carries an explicit comment establishing why it's safe (e.g. "No data loss: both dropped columns are all-NULL in every environment this migration has been checked against" for `qty_scrapped`/`qty_reusable`) — this migration carries no such justification, and none of the sibling migrations backfill `plan_finish` from it either.
- **severity:** High (data-loss risk from an unmitigated destructive migration against a table that predates this branch and is very likely to hold real rows in the dev/staging Supabase DB by now, given the system has been in active use since Sprint 13). Not scored Critical — this is a data-integrity defect, not a security exposure (no leak/bypass/RCE/creds) — but per `CLAUDE.md` §5.2 and `qa.md`, High findings BLOCK the same as Critical.
- **evidence:** `grep -rn due_date backend/prisma/migrations/` shows the column originating in `20260615120000_sprint13_manufacturing_order` and being read/written in `manufacturing-orders.service.ts` (lines 151, 582, 643-644 on `origin/dev`) and rendered in `MoDetail.tsx` (`<Row k="Due Date" v={fmtDay(mo.due_date)} />` on `origin/dev`). The new migration's full text has zero `UPDATE`/backfill statements.
- **note on the CI gate:** `.github/workflows/migrate-deploy.yml`'s IS8 check (`Check for destructive migrations`) will **not** catch this — it only greps the `prisma migrate diff` output for `DROP COLUMN|DROP TABLE|RENAME COLUMN|RENAME TABLE` and requires the `migrate-allow-destructive: true` commit-message flag (present on `aacfbf3`) to proceed. That gate confirms the destructive operation was *acknowledged*, not that it is *data-safe* — it does not check for a backfill. This finding is exactly the kind of check that gate cannot perform and a human/QA pass must.
- **fix_route:** data/backend — either (a) add a follow-up migration that backfills `plan_finish = due_date::timestamptz` (or `actual_finish`, whichever is the intended successor semantic — needs a product-owner call, since `due_date` was a single deadline and the new model splits plan vs. actual) before/in place of the bare `DROP COLUMN`, or (b) have data/devops run `SELECT count(*) FROM manufacturing_order WHERE due_date IS NOT NULL` against the dev and staging DBs directly (this pass deliberately did not do so itself — staging credentials are user-managed per this project's own convention) and only proceed as-is if that count is confirmed zero everywhere this migration will run.

**F-003 (Medium → WARN)**
- **where:** `backend/src/modules/manufacturing-orders/mo-print/mo-print-pdf-builder.spec.ts`
- **what:** Fails intermittently under the full `npx jest` run (`Assembly Part List (after the MO page) › adds no page at all when there are no assemblies` — "Exceeded timeout of 5000ms") but passes cleanly 35/35 when re-run in isolation. - **severity:** Medium — not a functional regression (isolated re-run confirms correct behavior), but a real CI-flakiness risk: per `qa.md`'s own Step 4 ("Red CI = immediate BLOCK, no further check needed"), an intermittent timeout on an unrelated PR could trigger a false BLOCK later, or mask a real regression behind an assumption of "it's just flaky."
- **evidence:** Full-suite run: `FAIL ... mo-print-pdf-builder.spec.ts (152.908 s)` with one timeout. Isolated re-run: `PASS ... mo-print-pdf-builder.spec.ts (16.277 s)`, `Tests: 35 passed, 35 total`.

**F-004 (Medium → WARN)**
- **where:** `backend/src/modules/work-orders/wo-auto-create.service.ts` — `computeMarkBudget()` / `assertMarkBudgets()`
- **what:** The mark-budget guard (rejects a WO-mark request that would exceed what's left of an MO assembly line's qty after sibling WOs of the same operation) is check-then-act with no row-level locking (`SELECT ... FOR UPDATE`) and no DB-level backstop — the only unique index on `work_order_mark` is `(work_order_id, bom_assembly_id)`, which prevents the same mark twice on the same WO but does nothing to cap the sum across sibling WOs. Two concurrent `createOrAddMarks()` calls for the same `(mo_id, operationId, bom_assembly_id)` could both read the same "committed" total, both pass validation, and jointly over-commit the mark's budget.
- **severity:** Medium — a genuine TOCTOU gap with no safety net, but bounded impact: this is an internal, manually-triggered admin action (a factory admin creating a WO), not a public high-concurrency endpoint, and the worst case is a correctable over-commitment, not data loss or a security issue.
- **evidence:** `computeMarkBudget()` (line ~395-413) and `assertMarkBudgets()` (line ~422-442) both read via plain `findMany`, inside the caller's transaction, with no `FOR UPDATE`/serializable isolation; `wo-auto-create.service.spec.ts` tests the sequential logic thoroughly but has no concurrent-transaction test (expected for a unit-test-with-mocked-`tx` style — this is not a test-coverage gap, it's an implementation gap unit tests structurally can't exercise).
- **fix_route:** backend — add `SELECT ... FOR UPDATE` scoped to the relevant `work_order_mark` rows (same pattern already used for `work_order_code_seq` in the same file), or run the check+insert under `Prisma.TransactionIsolationLevel.Serializable` with retry-on-conflict.
